Security

Copse treats every repository, server and remote it talks to as untrusted, and it's built so that nothing you've committed is ever lost by accident. Here's what that means, how to check what you download, and how to tell us about a problem.

Found a security problem? Please don't open a public issue. Report it privately with the Report a vulnerability button on the repository's Security tab, so it can be fixed before it's public. You'll get a reply within a week.

Everything is checked

Every object Copse receives is hashed again before it's kept, and every pack's checksum is verified. Anything whose contents don't match its id is refused.

Hostile repositories

A crafted repository can't make a checkout write outside your project, into .copse, or through a symlink, and addresses can't smuggle options into ssh. The test suite attacks Copse with exactly these.

Nothing lost

Every move of a branch is recorded, so copse undo can put it back. Anything that would throw work away, such as reset --hard or restore, keeps a backup first.

What counts as a security problem

  • A repository, pack or server reply that makes Copse write outside the working folder, into .copse, or through a symlink.
  • Objects accepted whose contents don't match their ids.
  • Command or option injection through URLs, remote names, submodule addresses or file names.
  • Credentials shown, logged or sent somewhere they shouldn't go.
  • A crash or hang caused by data from a server or someone else's repository.

Helpful things to include in a report: what an attacker could do, the version (copse version), and steps or a repository that shows it.

Signing in

Copse uses git's own credential helpers, so a login you've saved for git (for example in the macOS Keychain) works for Copse too, and Copse doesn't keep a password store of its own. Over SSH it uses your SSH key, as git does. It asks for a login only when the server needs one, and it never prints a password.

A login written into an address (https://user:token@host/…) works, but it's kept in .copse/remotes, so a credential helper is the safer choice.

Signed commits and tags

Sign with an SSH key or GPG, using the same settings as git. Signatures are stored the way git stores them, so git verifies Copse's, Copse verifies git's, and GitHub shows them as Verified.

copse config --global user.signingKey ~/.ssh/id_ed25519
copse config --global gpg.format ssh
copse commit -S -m "Signed"
copse verify-commit HEAD

copse tag -s makes a signed tag and copse verify-tag checks one. Set gpg.ssh.allowedSignersFile and verifying also checks that the key belongs to the commit's author.

Checking your copy of a repository

copse fsck

Checks that every object is intact, and that everything your branches, tags, stashes and undo history need is there.

Checking what you download

Each release comes with a SHA256SUMS file. Put it next to the archive and run:

shasum -a 256 -c SHA256SUMS --ignore-missing

Releases are built from the public source by GitHub Actions, where every change is also scanned by CodeQL and the dependencies are checked against known vulnerabilities (cargo audit).

Copse isn't signed with an Apple developer certificate yet, so macOS quarantines a copy downloaded in a browser; see Install. Homebrew and curl downloads aren't affected.

Supported versions

Until 1.0, fixes go into the latest release only. The nightly build gets them first.
